# W07 실행·재현 안내

## 대상과 범위

- 앱: https://aurora-ops-q341.axhub.app/ (lounge, aurora-ops-q341, Docker)
- 핵심 결정: 영업지원팀과 영업임원이 관련 거래처의 월 판매장려금을 합산 검토하고 승인한다.
- 내부 처리: 계산, 승인·보류, 소명 요청·답변·재상신, 서류 후보 확인, 계좌 변경과 재검토, 회계 증빙 확인, DB 이력 저장.
- 가상 입력: 추가 시나리오 서류와 대리점 회신, 승인·확인 역할의 시연 입력. 외부 발송·은행 지급은 수행하지 않는다.
- 끝 상태: 회계의 지급 검토 가능. 실제 지급 완료나 은행 대사 완료를 뜻하지 않는다.

## 개발·실행 환경

Node.js 22, npm, PostgreSQL, S3 호환 저장소를 사용한다. `npm ci` 후 `npm test`로 자동 테스트, `npm start`로 서버를 실행한다. 기본 포트는 8080이며 PORT로 변경할 수 있다.

런타임 환경변수는 AXHub에서 설정한다. DATABASE_URL, STORAGE_ENDPOINT, STORAGE_BUCKET, STORAGE_ACCESS_KEY, STORAGE_SECRET_KEY, GOOGLE_API_KEY, CONNECTION_CHECK_TOKEN이 필요하다. GOOGLE_MODEL은 선택 사항이다. 키나 비밀값을 코드·git에 넣지 않는다.

원본은 `01_참가자_배포용/04_원본데이터` 아래 `m_agency_cv.csv`, `sales_rebate_payment_cv.csv`, `fin_collection_history_cv.csv`다. 로컬 테스트는 원본을 읽기만 한다. 배포 서버는 S3의 `w07/source-csvs.json`에 등록된 세 CSV 문자열을 읽는다. 초기 자료 등록용 PUT `/api/internal/w07-sources`는 `x-connection-check-token`으로 보호된다. 이미 등록된 운영 원본은 재등록할 필요 없다. Docker 이미지에 원본 폴더를 복사하지 않는다.

검산 주소: GET `/api/w07/2026-06`. 원본 40행, 관련 묶음 1개, 전결 37요청, 임원 1요청, 임원 합계 3,888,097원이다.

## 입력 시점과 출처

아래 재현 사례의 업무 발생일·적용일은 **추가 시나리오 가정인 2026-07-01**, 적용 정산월은 **2026-06**으로 입력한다. 실제 기록 시각은 서버가 별도로 저장한다. 입력일이 과거여도 예약 실행이 아니라 선택한 정산월에 즉시 적용한다. 자료 구분은 준비된 서류면 추가 시나리오 자료, 직접 작성한 답변·확인이면 가상 회신·직접 입력으로 선택한다. 실제 확보된 증빙이라고 주장하지 않는다.

## 대표 사례

각 사례는 독립적으로 시작한다. 시연 전 같은 월 기록을 지워야 하면 테스트 DB에서만 초기화한다(운영 검토 중에는 초기화하지 않는다). 아래 이름은 화면 용어다(팀 승인 = 원본 정책의 영업지원팀 전결).

### 1. 정상 — 팀 승인 일괄 지급과 지난 지급 점검

1. 영업지원팀 홈: 오늘 할 일에 "6월 팀 승인 37건 · 일괄 승인"이 보인다. 승인 요청 목록에서 37건(33,271,715원)을 선택해 승인한다.
2. 회계 지급 검토: "지급 반영 · 일괄"에서 지급 시스템에 반영한다. 모의 배치 번호가 각 건 이력에 남는다(실지급 아님).
3. 회계 지난 지급 점검: 금강상사11 외 2곳 1~5월 15건 22,238,349원. 원인 한 줄(등록일이 첫 지급 전)을 확인하고 결론 "감사 보고"를 저장한다. 영업지원팀·영업임원은 같은 화면을 보기만 한다.

### 2. 정보 부족 → 보완 요청 → 재답변 → 조건부 승인 (필수 확장 + 다른 부서 영향)

1. 영업임원이 금강상사11 외 2곳을 거절한다. 의견: `공동 입금계좌 사용 경위와 실제 수취계좌가 확인되지 않음. D-037 대표자가 같은 사람인지도 확인 필요.`
2. 영업지원팀 → 거래처 확인 → 요청 작성: AI가 임원 의견을 보고 항목(공동 계좌 이유, 받을 계좌와 예금주, 대표자 동일인)을 체크해 둔다. "왜 이 항목인가요?"에서 근거를 확인하고 기한을 정해 보낸다.
3. 대리점 금강상사11은 세 항목 모두, 성일상사24는 공동 계좌 이유만 답한다. 대륙상사37은 답하지 않는다.
4. 영업지원팀 답변 검토: 거래처별 칸(초록 답함/빨강 이 항목 답 없음/회색 미답변)과 AI 판정이 보인다. 미답변 거래처가 있어 '부분'이다. "보낼 내용 보기"에서 부족한 항목이 성일상사24·대륙상사37에게만 가는지 확인하고 보완 요청을 보낸다.
5. 두 거래처가 답한다. AI 판정이 모두 '충족'이면 "확인 완료 · 임원에게 다시 올리기"를 누른다.
6. 영업임원 결정: "지난 결정 이후 확인된 점"을 보고 승인. AI가 고른 조건(받는 계좌 예금주 확인, 공동 계좌 이유 확인서)을 그대로 두거나 바꾼다. 사례 1에서 감사 보고로 결론 났다면 "다음 3개월 사전 확인" 조건도 보인다.
7. 회계 지급 검토: 조건 0/2 · 지급 보류. 조건마다 확인 방법과 결과를 적어 "확인함" → 2/2가 되면 지급 시스템에 반영한다. 임원이 붙인 조건이 회계의 완료 조건이 되는 것이 다른 부서 영향이다.

### 3. 변경 — 확인 중 거래처 계좌 변경

1. 사례 2의 2단계까지 진행한다.
2. 대리점 금강상사11 → 서류 → 등록 정보 변경 신청(정산계좌, 새 계좌, 사유, 첨부 이름)을 보낸다.
3. 영업지원팀 서류 확인: AI가 읽은 값과 등록 정보를 나란히 비교한다. 확인 메모를 남겨 저장하고 "변경 적용".
4. 정보 변경 화면: 이번 달은 3곳 묶음·임원 승인 그대로, 다음 달부터 새 정보로 판단. 같은 계좌 입금 기록이 근거다. 진행 중인 거래처 확인은 이어서 하고, 다시 올리면 임원이 재검토, 회계가 다시 확인한다.

### 4. 승인 거절과 이의 제기

1. 영업임원이 "추가 확인 요청" 또는 "거절"을 고르면 의견이 필수다. 영업지원팀 상세의 "다음 단계"가 "확인 요청 만들기"로 바뀐다.
2. 영업지원팀이 "묶음이 잘못됐나요?"로 이의를 제기하면 관리자 항목·조건 목록 화면에 올라오고, 관리자가 유지/받아들임으로 처리한다. 이의 제기 중에도 요청은 그대로 진행되며 원본은 바뀌지 않는다.

## AI·사람·도구와 다른 부서 영향

| 기능 | AI의 실제 역할 | 사람·도구로 이어지는 위치 |
|---|---|---|
| 확인 항목 제안 | 임원 의견을 읽고 허용 목록에서 1~4개 선택, 근거 문구 인용. 목록 밖은 새 항목 제안으로만 | 영업지원팀 확정·발송 → 거래처별 항목 양식 생성 → 관리자 목록 승인 |
| 거래처 답변 판정 | 항목별 충족·부분·부족과 인용. 코드가 인용 대조·미답변 거래처 강등 | 보완 요청 범위(항목×거래처) 자동 계산 → 담당자 결정 → 임원에게 다시 올리기 |
| 승인 조건 제안 | 근거 있는 조건 후보 중 1~3개 선택 | 임원 선택 → 회계 확인 항목 → 모두 확인 전 지급 반영 불가 |
| 서류 읽기 | 대표자·주소·계좌 후보 추출 | 등록 정보 비교 → 변경 적용 → 재계산·임원 재검토 → 회계 재확인 |

필수 확장으로 제시할 내용은 **건별 확인 항목과 거래처별 답변 판정, 조건부 승인, 서류 확인과 계좌 변경의 영향 추적**이다. 임원이 붙인 조건이 회계의 확인 항목이 되어 회계 작업의 완료 조건을 바꾸는 것이 다른 부서 영향의 직접 반영이다(사례 2). 회계의 목표·제약은 미확인 수취정보로 지급 검토를 진행하지 않는 것이며, 영업의 변경으로 기존 회계 작업이 확인 대기로 돌아가고 회계가 별도 자료를 확인해야 한다. 이 연결을 사례 3으로 확인한다. 이는 참가자가 정의한 통제이며 원본에 완성된 절차가 있는 것으로 설명하지 않는다.

확인된 효과는 개별 0건 대비 합산 1건의 임원 대상 식별, 같은 그룹 1~5월 한도 초과 팀 승인 지급 15건(22,238,349원)의 사후 검토 연결, 변경 후 관련 요청·과거 지급 대상 연결, 예외 상태 전환이다. 실제 처리시간 단축·손실 예방 금액은 측정하지 않았으므로 성과로 단정하지 않는다.

## 검증과 제한

`npm test`는 원본 계산, 관련자 전이 연결, 임원 건 일괄 승인 제외, 항목 제안 검증(목록 밖 거부·인용 대조), 거래처별 답변 합치기와 보완 범위 계산, 미답변 거래처 강등, 조건 미확인 시 지급 차단, 지난 지급 점검 결론과 3개월 사전 확인 조건, 원인 계산, 역할별 화면 접근(대리점은 자기 항목만), 관리자 목록을 검사한다. `TEST_DATABASE_URL`(로컬 전용)을 주면 PostgreSQL 통합 테스트가 정상(일괄 지급)·조건부 승인·거절→보완→재답변·확인 중 변경·승인 후 변경과 이의 제기·목록 관리를 끝까지 실행한다. 화면 테스트와 통합 테스트는 가짜 AI를 쓰므로 실제 Gemini 품질의 증거를 대신하지 않는다.

실제 작동: 계산·상태 변화·DB 기록·Gemini 호출. 모의 처리: 지급 시스템 반영(배치 번호 기록), 알림(앱 안 벨), 첨부(파일 이름·위치 입력), 로그인(역할 선택). 범위 밖: 은행 실행, 메일 발송, 파일 업로드·PDF 읽기, 다음 달 묶음 분리.
