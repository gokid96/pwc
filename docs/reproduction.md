# W07 실행·재현 안내

## 대상과 범위

- 앱: https://aurora-ops-q341.axhub.app/ (lounge, aurora-ops-q341, Docker)
- 핵심 결정: 영업지원팀과 영업임원이 관련 거래처의 월 판매장려금을 합산 검토하고 승인한다.
- 내부 처리: 계산, 승인·보류, 소명 요청·답변·재상신, 서류 후보 확인, 계좌 변경과 재검토, 회계 증빙 확인, DB 이력 저장.
- 가상 입력: 추가 시나리오 서류와 대리점 회신, 승인·확인 역할의 시연 입력. 외부 발송·은행 지급은 수행하지 않는다.
- 끝 상태: 회계의 지급 검토 가능. 실제 지급 완료나 은행 대사 완료를 뜻하지 않는다.

## 개발·실행 환경

Node.js 22, npm, PostgreSQL, S3 호환 저장소를 사용한다. `npm ci` 후 `npm test`로 자동 테스트, `npm start`로 서버를 실행한다. 기본 포트는 8080이며 PORT로 변경할 수 있다.

런타임 환경변수는 AXHub에서 설정한다. DATABASE_URL, STORAGE_ENDPOINT, STORAGE_BUCKET, STORAGE_ACCESS_KEY, STORAGE_SECRET_KEY, GOOGLE_API_KEY, CONNECTION_CHECK_TOKEN이 필요하다. GOOGLE_MODEL은 선택 사항이다. 키나 비밀값을 코드·git에 넣지 않는다.

원본은 `01_참가자_배포용/04_원본데이터` 아래 `m_agency_cv.csv`, `sales_rebate_payment_cv.csv`, `fin_collection_history_cv.csv`다. 로컬 테스트는 원본을 읽기만 한다. 배포 서버는 S3의 `w07/source-csvs.json`에 등록된 세 CSV 문자열을 읽는다. 초기 자료 등록용 PUT `/api/internal/w07-sources`는 `x-connection-check-token`으로 보호된다. 이미 등록된 운영 원본은 재등록할 필요 없다. Docker 이미지에 원본 폴더를 복사하지 않는다.

검산 주소: GET `/api/w07/2026-06`. 원본 40행, 관련 묶음 1개, 전결 37요청, 임원 1요청, 임원 합계 3,888,097원이다.

## 입력 시점과 출처

아래 재현 사례의 업무 발생일·적용일은 **추가 시나리오 가정인 2026-07-01**, 적용 정산월은 **2026-06**으로 입력한다. 실제 기록 시각은 서버가 별도로 저장한다. 입력일이 과거여도 예약 실행이 아니라 선택한 정산월에 즉시 적용한다. 자료 구분은 준비된 서류면 추가 시나리오 자료, 직접 작성한 답변·확인이면 가상 회신·직접 입력으로 선택한다. 실제 확보된 증빙이라고 주장하지 않는다.

## 대표 사례

각 사례는 독립적으로 시작한다. 공유 앱에서 초기화하면 다른 사용자의 해당 월 기록도 지워지므로, 시연 전에 현재 기록을 보존할 필요가 없는지 확인한 후 설정의 정산월 초기화를 실행한다. 운영 검토 중에는 초기화하지 않는다.

### 1. 정상 승인 → 회계 확인

1. 영업지원팀으로 6월을 선택한다. 전체 38요청, 전결 37요청, 임원 1요청을 확인한다. 목록 위 "과거 권한 초과 지급"에서 1~5월 15건·22,238,349원이 영업지원팀 전결로 지급됐음을 확인하고 사후 검토를 요청한다. 회계 작업 화면에서 회계가 검토 의견을 등록한다.
2. D-011 상세에서 D-011·D-024·D-037 연결 근거와 합계 3,888,097원을 확인한다. 단독 거래처 전결 건은 별도로 승인 가능하다.
3. 영업임원으로 D-011을 연다. 승인 조건 4개가 근거와 함께 표시되고 AI가 우선 조건을 체크한다. 통장 사본 수취계좌 확인·공동 계좌 경위서 확인 두 조건으로 승인한다. 회계 역할에서 "임원 승인 조건 · 0/2 확인"과 지급 증빙 확인이 막혀 있는지 확인한다.
4. 회계가 조건마다 확인 자료와 내용을 입력해 조건 확인을 저장한다. 모든 조건이 확인되면 지급 증빙 입력이 열린다. 회계 확인에 발생일·적용일과 자료 출처를 입력한다. 확인 자료 예: `추가 시나리오 지급 수취 확인서 A-01`. 확인 내용 예: `세 거래처별 수취 명의와 지정 계좌를 확인했다는 가상 확인 회신`. 실증빙을 확보한 것으로 설명하지 않는다.
5. 지급 증빙 확인 후 지급 검토 가능, 확인 자료·내용·시각의 이력을 확인한다. 실제 지급은 발생하지 않는다.

### 2. 거절 → 부족한 답변 → 재요청 → 재상신

1. 영업임원이 D-011을 거절한다. 사유: `공동 입금계좌 사용 경위와 실제 수취계좌 미확인`.
2. 영업지원팀의 소명 요청에서 AI 초안을 요청한다. 제안 증빙과 수신 거래처 자신의 사실만 담긴 문안을 검토·수정한다. 발생일·적용일을 입력하고 요청을 등록한다.
3. 대리점 역할에서 D-011을 선택하고 `같은 계좌를 사용했습니다. 상세 자료는 없습니다.`라고 가상 답변한다.
4. 영업지원팀이 답변 검토를 열면 AI 답변 판정이 항목별 충족·불명확·부족과 인용 문장을 보여 주고, 보완 요청 초안이 작성란에 들어간다. 담당자가 초안을 확인·수정해 보완 요청을 등록한다. 이력에 "AI 의견 보완 요청 · 담당자 결정과 같음"이 남는다. 대리점 답변 화면에는 미충족 항목이 표시된다.
5. 대리점이 `공동 정산 담당자가 입금을 모아 처리했습니다. 거래처별 수취계좌와 명의 확인 내용은 별도 확인서 A-02에 기록했습니다.`라고 추가 답변한다. 이 내용은 시나리오 가정이다.
6. 영업지원팀이 확인 근거를 남기고 확인 완료 → 재상신한다. 임원은 이전 거절·요청·답변을 보고 승인한다. 회계는 사례 1처럼 별도로 확인한다.
7. 부족한 답변·재요청·재상신 이력이 남고 전결 37건이 영향을 받지 않는지 확인한다.

### 3. 소명 중 또는 승인 후 계좌 변경

1. D-011에 사례 2의 소명 요청을 등록한 상태에서 시작한다. 별도 반복 시에는 사례 1의 승인 이후 상태에서 시작해 두 갈래를 확인한다.
2. 대리점 D-011의 서류 접수에서 계좌 변경 신청서를 선택한다. 출처와 시점을 입력해 접수한다. 혼합 회신서를 사용하면 기존·새 계좌 후보 모두 확인 대상으로 표시되는지도 확인할 수 있다.
3. 영업지원팀은 원문과 AI 추출 후보를 비교한다. AI가 실패하면 수정/직접 입력을 선택한다. 대표자·주소는 원본과 대조하고 계좌는 신청서의 새 값만 확인한다. 근거를 남겨 저장한다.
4. 변경 적용의 발생일·적용일·정산월을 입력하고 확인된 계좌 변경을 적용한다.
5. 등록정보 계산은 D-011·D-024 2,562,561원과 D-037 1,325,536원으로 나뉘지만, 실제 업무는 동일 입금계좌 정황으로 기존 합계 3,888,097원과 임원 경로를 유지하는지 확인한다.
6. 기존 소명 요청이 있으면 이어 처리한다. 충분하지 않으면 재요청, 확인되면 재상신한다. 임원 승인 후 회계에서 증빙을 다시 확인한다. 기존 승인은 이력으로 남는다.
7. 같은 그룹의 1~5월 원본 승인 15행이 사후 검토 대상으로 보이고, 이미 지급된 원본은 변경되지 않는지 확인한다.

## AI·사람·도구와 다른 부서 영향

| 기능 | AI의 실제 역할 | 사람·도구로 이어지는 위치 |
|---|---|---|
| 소명 답변 판정 | 답변을 확인 항목별로 충족·불명확·부족 판정하고 근거 문장 인용. 인용은 코드가 원문 대조 | 영업지원팀이 보완 요청/확인 완료 결정 → 미충족 항목이 대리점 화면에 표시 → 재답변 → 재판정 |
| 승인 조건 제안 | 코드가 만든 근거 있는 조건 후보 중 1~3개를 우선순위로 선택 | 임원이 선택·조건부 승인 → 회계 확인 항목 생성 → 모두 확인 전 지급 증빙 확인 불가 |
| 소명 초안 (첫 요청) | 통장 사본·사업자등록증·공동 계좌 사용 경위서 중 증빙 선택. 문안은 수신처 사실로 코드가 구성 | 영업지원팀 수정·등록 → 대리점 답변 → 확인/재요청 |
| 서류 추출 | 원문에 존재하는 대표자·주소·계좌 후보 추출 | 영업지원팀 확인 → 별도 변경 기록 → 재계산·임원 재검토 → 회계 확인 대기 |

필수 확장으로 제시할 내용은 **소명 답변 판정과 조건부 승인, 서류 후보 확인과 계좌 변경의 영향 추적**이다. 임원이 붙인 조건이 회계의 확인 항목이 되어 회계 작업의 완료 조건을 바꾸는 것이 다른 부서 영향의 직접 반영이다(사례 1). 회계의 목표·제약은 미확인 수취정보로 지급 검토를 진행하지 않는 것이며, 영업의 변경으로 기존 회계 작업이 확인 대기로 돌아가고 회계가 별도 자료를 확인해야 한다. 이 연결을 사례 3으로 입증한다. 이는 참가자가 정의한 통제이며 원본에 완성된 절차가 있는 것으로 설명하지 않는다.

확인된 효과는 개별 0건 대비 합산 1건의 임원 대상 식별, 같은 그룹 1~5월 권한 초과 전결 지급 15건(22,238,349원)의 사후 검토 연결, 변경 후 관련 요청·과거 지급 대상 연결, 예외 상태 전환이다. 실제 처리시간 단축·손실 예방 금액은 측정하지 않았으므로 성과로 단정하지 않는다.

## 검증과 제한

`npm test`는 원본 계산, 관련자 전이 연결, 임원 건 일괄 승인 제외, 불충분 답변 재요청, 변경 후 임원 경로 유지, 회계 재확인, AI 후보 검증과 실패 대체, 명시적 날짜와 근거 입력, 화면 상태 표시를 검사한다. AI 답변 판정의 인용 대조·근거 없는 충족 강등, 승인 조건 목록 외 응답 거부, 조건 미확인 시 지급 차단, 과거 초과 지급 15건 계산도 검사한다. `TEST_DATABASE_URL`(로컬 전용)을 주면 PostgreSQL 통합 테스트가 정상·조건부 승인·거절·변경 흐름을 끝까지 실행한다. 화면 테스트는 DB 스냅샷 대역과 가짜 AI를 사용하므로 실제 Gemini 품질이나 운영 DB 저장의 증거를 대신하지 않는다.

운영 화면·배포 확인 결과는 `docs/checklist.md`에 기록한다. 시연 영상·스크린샷이나 실제 실행 기록은 별도로 붙여야 한다. 로그인·신원 인증, 외부 발송, 이미지/PDF, 은행 실행, 다음 달 그룹 분리, 미래 예약 적용은 범위 밖이다.
