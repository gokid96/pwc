# W07 판매장려금 지급 검토 설계

이 시스템은 영업지원팀이 관련 거래처의 판매장려금을 함께 검토하도록 돕습니다.
영업임원은 금액과 근거, 소명 내용을 보고 승인 여부를 결정합니다.
회계 담당자는 승인과 증빙 상태를 확인해 지급 검토를 진행합니다.

## 원본 규칙과 계산

- 대표자·주소·정산계좌 중 두 항목 이상이 일치하는 거래처를 연결하고 간접 연결까지 같은 그룹으로 묶는다. 정산월별 그룹 합계가 200만원 이하면 영업지원팀 전결, 초과면 영업임원 승인이다. [승인 권한 정책](../01_참가자_배포용/04_원본데이터/00_common/approval_authority_policy.md) · [데이터 사전](../01_참가자_배포용/04_원본데이터/00_common/data_dictionary.md)
- 실제 입금계좌는 별도 정황으로 대조한다. 입금계좌를 지급 수취계좌로 단정하거나 그 일치만으로 등록정보를 바꾸지 않는다. [W07 안내](../01_참가자_배포용/세계관_BPMN/W07.html) · [데이터 사전](../01_참가자_배포용/04_원본데이터/00_common/data_dictionary.md)
- 원본 6월 40행은 승인 요청 38건이다. 단독 거래처 37건은 영업지원팀, D-011·D-024·D-037 합계 3,888,097원은 영업임원 대상이다. 원본 CSV는 읽기만 하며 변경·결정·이력은 별도로 저장한다.

## 역할과 화면

| 역할 | 화면과 할 일 |
|---|---|
| 영업지원팀 | 홈(오늘 할 일·알림 벨), 승인 요청 목록·상세, 거래처 확인(요청 작성·답변 검토), 서류 확인, 정보 변경, 지난 지급 점검(조회·회수 확인). 팀 승인과 일괄 승인, 임원에게 다시 알리기, 묶음 이의 제기, 확인할 점 "확인함"을 처리한다. |
| 영업임원 | 결정할 요청 카드 목록과 결정 화면. 승인 / 추가 확인 요청 / 거절 중 고르고, 승인이면 AI가 제안한 조건을 골라 붙인다. |
| 회계 | 지급 검토(승인 조건 확인, 팀 승인 일괄 지급 반영, 개별 지급 반영), 지난 지급 점검 결론. |
| 대리점 | 자기 거래처 홈, 항목별 답변 양식, 서류 제출과 등록 정보 변경 신청. 다른 거래처 금액·임원 의견은 보이지 않는다. |
| 관리자 | AI 사용 기록(사람이 따랐는지/바꿨는지), 확인 항목·승인 조건 목록 관리, 묶음 이의 제기 처리. |

처음 접속하면 역할을 고른다(실제 로그인 대신). 대리점은 목록에서 거래처를 고른다. 화면 용어는 업무를 모르는 사람 기준으로 바꿨다: 전결 → 팀 승인, 상신 → 임원에게 보냄, 소명 → 거래처 확인, 사후 검토 → 지난 지급 점검, 수취계좌 → 받는 계좌. 원본 정책 문서의 용어(전결 등)는 정책 인용에서만 쓴다. 각 화면은 맨 위에 결론 한 줄과 "다음 단계" 버튼 하나를 두고, 표·근거·원본 행 위치는 "자세히"로 접어 둔다. 상태는 색과 함께 ✓ / ! / ◷ 기호와 글자로 표시한다.

## 업무 흐름

1. 정산월을 선택하면 원본 거래처·장려금·회수 내역을 연결해 그룹과 승인권자를 계산한다. 1~5월은 지급된 원본 기록을 조회하고, 원본에 미지급 건이 있는 월에만 승인과 후속 작업을 한다.
2. 승인권자가 승인하면 회계 지급 검토 작업이 생긴다. 필요한 증빙이 확인되지 않으면 확인 대기로 두고, 회계 담당자의 확인 후 지급 검토 가능으로 바뀐다. 실제 지급이나 은행 대사는 수행하지 않는다.
3. 임원 거절 또는 추가 확인 요청 시 해당 건을 보류한다. 영업지원팀은 소명 요청을 작성·발송하고 대리점의 답변을 검토한다. 부족하면 재요청하고 충분하면 확인 후 임원에게 재상신한다. 기존 이력은 남으며 다른 전결 건은 독립적으로 진행한다. 발송과 답변은 앱 내부 기록이다.
4. 대리점은 텍스트를 직접 입력하거나 `.txt`로 접수한다. 영업지원팀은 추출 후보와 원문을 확인해 수락·수정·반려한다. 확인된 계좌 변경만 별도 기록에 적용하고 원본을 수정하지 않는다. 서류 접수와 변경 적용은 처리 이력에 남는다.

## 계좌 변경과 재검토

- 변경 전후 그룹과 합계·승인권자를 재계산하고, 영향을 받는 거래처는 변경 전후 그룹의 연결을 따라 찾는다. 기존 승인과 회계 작업을 삭제하지 않고 재검토 필요 및 확인 대기로 표시한다.
- 기존 임원 대상 그룹이 분리되더라도 해당 그룹에 둘 이상의 거래처가 같은 입금계좌를 사용한 기록이 남으면 기존 임원 경로를 유지한다. 등록정보 기준 재계산 결과와 유지 근거를 함께 표시한다. 입금계좌 일치는 지급 수취계좌 확정이나 단독 그룹 생성 근거가 아니다.
- 기존 소명 요청이 있으면 이어서 사용한다. 소명 확인 후 임원이 기존 승인·거절·추가 확인 선택지로 재검토한다. 승인하면 보류가 해제되고 회계는 증빙을 다시 확인한다.
- 영향 범위에 속하는 거래처의 같은 해 이전 월 원본 승인 기록도 재검토 목록에 올린다. 지급일이 있는 기록은 사후 검토 대상으로 표시하며 이미 지급된 건을 되돌리지 않는다. 6월 D-011·D-024·D-037은 이번 달 처리 종료까지 기존 세 거래처 합산과 임원 경로를 유지한다.

## AI와 Gemini 전송 범위

서버가 `GOOGLE_API_KEY` 환경변수로 Google Gemini API를 호출한다. 기본 모델은 `gemini-3.1-flash-lite`이며 `GOOGLE_MODEL`로 변경할 수 있다. 요청·응답 또는 실패 사유는 앱의 AI 호출 기록에 저장한다. AI는 승인하거나 등록 정보를 확정하지 않는다.

| 기능 | Gemini에 보내는 정보 | 결과와 사람의 역할 |
|---|---|---|
| 확인 항목 제안 | 임원 거절·추가 확인 사유 원문, 거래처 ID와 일치 항목명, 코드가 근거를 계산한 허용 항목 목록. 금액·이름·주소·계좌번호는 보내지 않는다. | Gemini가 허용 목록에서 1~4개를 고르고 근거 문구를 인용한다. 코드가 목록 밖 응답을 버리고 인용이 사유 원문에 없으면 지운다. 목록에 없는 항목은 "새 항목 제안"으로만 저장되며 관리자가 승인해야 쓸 수 있다. 영업지원팀이 항목·기한을 확정해 보낸다. |
| 거래처 답변 판정 | 보낸 항목(이름·형식·필수 첨부), 거래처별 답변 모음. 답변에 대리점이 적은 계좌·예금주가 포함될 수 있다. | 항목마다 충족·부분·부족과 근거 인용. 코드가 인용을 답변 원문과 대조하고, 근거 없는 충족과 받을 곳 중 미답변 거래처가 있는 충족을 '부분'으로 낮춘다. 보완 요청은 부족한 항목을 그 항목에 답하지 않은 거래처에만 보낸다. 담당자가 보완 요청 / 확인 완료 · 임원에게 다시 올리기를 결정하고 AI 의견과의 일치 여부를 남긴다. |
| 승인 조건 제안 | 거래처 ID, 일치 항목명, 입금계좌가 같은 거래처 ID, 근거가 있는 조건 목록과 근거 문장, 최근 답변 판정 결과. 금액·이름·주소·계좌번호는 보내지 않는다. | 코드가 근거 있는 조건만 후보로 만든다. 지난 지급 점검 결론이 감사 보고·회수 검토면 "다음 3개월 사전 확인"이 후보에 추가된다. Gemini는 1~3개를 고른다. 임원이 조건을 골라 승인하면 회계 확인 항목이 되고, 모두 확인되기 전에는 지급 반영이 막힌다. |
| 서류 읽기 | 선택한 서류 텍스트 전체. 서류에 적힌 이름·주소·계좌번호가 포함될 수 있다. | 대표자·주소·계좌 후보를 원문 줄과 대조한다. 담당자가 등록 정보와 비교 화면에서 고치거나 그대로 저장하고, 계좌 변경이면 적용한다. |

## 원본에 없는 프로젝트 가정

- 거절 후 소명 요청·답변 검토·재요청·재상신, 역할별 화면과 상태, 회계 확인 대기는 프로젝트에서 정한 절차다.
- 계좌 변경 시 기존 임원 경로 유지와 변경 전후 그룹 및 이전 지급 건의 재검토 범위는 프로젝트에서 정한 통제다. 원본 정책이 변경 후 절차를 구체적으로 정하지 않는다.
- 통장 사본, 사업자등록증, 공동 계좌 사용 경위서 중 필요한 증빙을 제안하는 기준은 프로젝트 가정이며 적절성과 충족 여부는 담당자가 판단한다.
- 제공된 서류 양식과 입력된 소명·변경 내용은 업무 흐름 확인을 위한 추가 자료다. AI 결과는 후보이며 사실 확정의 근거가 아니다.

## 출처·시점 관리 (2026-11-12 보완)

서류와 소명·회계 확인 입력에는 자료 구분(추가 시나리오 자료 / 가상 회신·직접 입력), 업무 발생일, 적용일, 적용 정산월을 저장한다. 시스템 기록 시각과 구분하며 기존 기록에 없는 날짜는 만들어 넣지 않고 미기록으로 표시한다. 입력 적용일은 사건의 업무상 날짜이고, 선택한 정산월에 저장 즉시 반영한다. 미래 예약 적용이나 여러 월로 자동 전파하는 기능은 없다. 2026-07-01 가상 기준일과 개발·시연의 실제 시각을 혼동하지 않는다. [A05 17·19~20쪽]

원본 규칙은 2개 항목 일치·전이 연결·월 200만원 한도·실입금 대조다. 소명 재요청과 재상신, 변경 후 이번 달 임원 경로 유지, 이전 월 사후 검토, 증빙 종류와 회계 확인 대기는 프로젝트가 추가한 통제다. 회수계좌를 지급계좌로 단정하지 않으며 이미 지급된 금액을 되돌리지 않는다. [A06 W07 7쪽 / 프로젝트 가정]

## 검토 화면과 회계 근거 (이번 보완)

- 임원 목록은 전체 대상과 현재 결정할 요청을 구분한다. 상세의 현재 단계는 재상신 시 임원 재결정을 가리킨다.
- AI 결과에는 생성 시각과 기준을 표시한다. 승인 조건 제안은 근거(그룹·소명·결정 이력)가 바뀌면 다시 제안하며, 자동 승인은 하지 않는다.
- 회계 확인은 자료 이름·위치와 확인 내용을 별도 필수 입력으로 저장한다. 자료의 진위와 충분성은 담당자가 판단한다. 문자 입력만으로 실제 계좌 소유를 검증한 것으로 보지 않는다.
- 서류는 텍스트만 받으며, 이미지·PDF 첨부를 기대하지 않도록 접수 범위를 안내한다. 재검토 화면은 변경 내용, 유지 근거, 현재 담당 작업, 등록정보 계산 비교, 과거 사후 검토 순서로 제공한다.
- AI와 부서 영향, 정상·거절·변경 재현 절차는 [실행 안내](reproduction.md)를 따른다. 추가 필드와 상태 표현은 프로젝트 설계이며 원본 승인권한을 변경하지 않는다.

## AI 판정·승인 조건·과거 초과 지급 (2026-11-12 개선 · 아래 2026-11-13 재설계로 일부 바뀜)

- **과거 권한 초과 지급.** 같은 해 이전 정산월에서 그룹 합산이 한도를 넘었는데 원본상 모두 영업지원팀 전결로 지급된 건을 6월 목록에 표시한다. 원본 기준 D-011·D-024·D-037의 1~5월 15건, 22,238,349원이다. 지금은 시스템이 자동으로 올리고 회계가 결론 3가지 중 하나를 고른다. 지급된 금액은 되돌리지 않는다. W07의 질문 "합산을 놓치는 원인이 자료 분산인지 승인 단위인지"에 대해, 자료는 있었지만 거래처 단위로 승인한 것이 원인임을 원본으로 보여 준다.
- **소명 답변 판정(D).** 답변 검토 단계에서 자동으로 판정을 요청한다. 판정은 참고이며 상태를 바꾸는 것은 담당자의 보완 요청·확인 완료다.
- **승인 조건(C).** 임원 결정 화면에서 자동으로 조건을 제안한다. 조건부 승인은 기존 승인 권한(영업임원) 안에서 승인에 붙는 확인 항목이며 새 승인 단계를 만들지 않는다. 계좌 변경 후 재승인하면 이전 조건 확인은 무효가 되고 새 조건을 다시 확인한다.
- **대리점 화면.** 자기에게 온 항목과 보완이 필요한 항목만 보여 준다.
- 확인 항목 목록, 조건 목록, 조건과 근거의 대응은 프로젝트 가정이다. AI는 정해진 목록 밖의 값을 낼 수 없고, 목록 밖이거나 근거가 없는 응답은 버리거나 낮춘다.
- 기존 근거 요약(확인 문장 고르기)은 상태 변화로 이어지지 않아 제거했다.

## 화면 재설계와 업무 기능 추가 (2026-11-13)

- **건별 확인 항목.** 거래처 확인 요청의 항목은 고정 3개가 아니라 건마다 고른다. 항목마다 답변 형식(글/계좌·예금주/예/아니오), 필수 첨부, 받는 거래처가 있다. 대표자 항목은 대표자가 일치한 거래처에만 간다. 요청 기록에 항목·받는 곳·기한을 저장한다.
- **거래처별 답변.** 대리점은 자기에게 온 항목만 보고 항목별로 답한다. 여러 거래처가 각각 답하며, 기한 전까지 다시 보낼 수 있다(마지막 답이 유효).
- **지난 지급 점검.** 시스템이 과거 한도 초과 팀 승인 지급을 자동으로 올린다(영업지원팀 요청 단계 없음). 회계가 종결 / 감사 보고 / 회수 검토 중 하나로 결론 낸다. 원인은 거래처 등록일과 첫 지급일로 코드가 계산한다. 회수 검토면 영업지원팀 할 일이 생긴다.
- **지급 반영.** 회계는 팀 승인 건을 일괄로, 임원 승인 건은 조건 확인 후 개별로 지급 시스템에 반영한다. 실제 지급 시스템과 연결되어 있지 않아 모의 배치 번호(예: B-202607081030)를 기록한다.
- **묶음 이의 제기.** 영업지원팀이 동명이인 등 묶음 판정에 이의를 내면 관리자가 유지/받아들임으로 처리한다. 받아들여도 원본은 바꾸지 않고 원본 수정 요청으로 남긴다. 이의 제기 중에도 요청은 그대로 진행한다.
- **관리자 목록.** 확인 항목과 승인 조건을 추가·중지한다. 중지한 조건·항목은 다음 요청부터 후보에서 빠지고, 이미 보낸 요청은 바뀌지 않는다.
- 위 항목·형식·받는 곳 규칙, 결론 3가지, 이의 제기 절차는 모두 프로젝트 가정이다.

## 검토 반영 보완 (2026-11-13 오후)

- **원인 추정과 확인 구분.** 지난 지급 점검의 원인은 현재 등록 정보 기준 "추정"으로만 표시한다. 승인 당시의 대표자·주소·계좌 기록은 원본에 없으므로(W07 미해결 지점) 회계가 "승인 당시 등록 정보 확인"(같음/달랐음/확인 불가 + 근거)을 남기면 원인이 '승인 단위' 또는 '등록 정보 변경 관리'로 좁혀진다. 확인 없이 낸 결론은 "미확인 상태 결론"으로 기록한다.
- **표시 구분.** 화면 값마다 작은 표시를 붙인다: 원본(제공 자료) · 계산(시스템 계산) · 가상 회신(시연 입력) · 모의(가짜 외부 처리) · AI 제안 · 추정. 각 화면 아래 "표시 읽는 법"에 뜻을 둔다. [A05 6]
- **가상 업무일.** 업무 발생일 기본값은 기준일 2026-07-01이고, 그 정산월 기록의 마지막 업무일을 이어받는다. 답변 기한 기본값은 업무일 + 영업일 5일. 실제 입력 시각은 "기록 시각"으로 따로 보인다. [A05 2]
- **지급 계좌.** 지급은 등록 정산계좌로만 한다. 거래처가 답한 받을 계좌가 다르면 지급 반영을 막고 정산계좌 변경을 먼저 확인하게 한다. 지급 기록에 거래처별 지급 계좌·답한 계좌·일치 여부를 남긴다. [W07 교육용 가정: 회수계좌를 지급계좌로 단정하지 않음]
- **승인 당시 기록.** 승인 기록에 묶음 구성·거래처별 금액·합계·원본 행 위치를 저장한다. [W07 미해결 지점: 그룹별 지급액이 어느 승인에 반영됐는지 이력 없음]
- **은행 회신과 대사(모의).** 지급 반영 후 회계가 거래처별 지급됨/반려(사유)를 입력한다. 반려 → 영업지원팀 받는 계좌 재확인 → 반려분만 재지급 → 전부 지급이면 대사 완료. [W07 BPMN "지급 결과 대사", 보완 데이터 "처리결과·반려사유"]
- **3개월 사전 확인.** 감사 보고·회수 검토로 결론 난 묶음은 결론 다음 달부터 3개월 동안 팀 승인 범위여도 영업임원 결정 대상으로 올린다(권한을 넓히지 않고 상향만 함). 규칙과 일괄 승인 차단은 구현·테스트했지만 원본에 7월 이후 자료가 없어 화면 시연은 할 수 없다(설계 단계 표시).
- **시연 초기화.** 관리자 화면에서 "정산월 초기화" 문구를 입력해야 그 달 앱 기록만 지운다. 원본 CSV와 항목 목록은 지우지 않는다.
- 화면 메뉴는 원본 용어를 함께 적는다: 거래처 확인(소명), 지난 지급 점검(사후 검토), 팀 승인(전결) 한도.
