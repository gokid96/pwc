# W07 판매장려금 지급 검토 설계

이 시스템은 영업지원 담당자가 이번 달 판매장려금을 어느 거래처끼리 합쳐 볼지 판단하도록 돕습니다.
합친 금액과 계좌 증거를 보여줘 담당자가 누구에게 승인을 요청하고 대리점에 무엇을 확인할지 정할 수 있게 합니다.
승인과 확인 결과를 기록해 회계 담당자가 어떤 건의 지급을 검토할 수 있는지 알려줍니다.

## 승인정책과 설계 범위

- 관련 거래처는 마스터의 대표자·주소·정산계좌 중 두 항목 이상 일치하면 연결하고, 간접 연결까지 같은 그룹으로 묶는다. 월 합산액 200만원 이하는 영업지원팀 전결, 초과는 영업임원 승인이다. 단독 거래처도 같은 한도를 적용한다. AI는 승인하거나 등록 정보를 확정하지 않는다. [승인정책](../01_참가자_배포용/04_원본데이터/00_common/approval_authority_policy.md) · [데이터 사전](../01_참가자_배포용/04_원본데이터/00_common/data_dictionary.md)
- 회수계좌는 등록 정보와 대조할 증거로 표시한다. 회수계좌만으로 마스터를 갱신하거나 판매장려금 수취계좌를 확정하지 않는다. 관련 정황은 소명·감사 검토에 사용한다. 상세 변경·재검토 절차는 아래의 교육용 구현안이다. [W07 안내](../01_참가자_배포용/세계관_BPMN/W07.html) · [A05](../01_참가자_배포용/A05.html)

## 기본 흐름

1. **정산월 선택.** 영업지원이 월을 선택하면 판매장려금의 `period_ym`을 조회하고 `agency_id`로 마스터를 연결한다. 원본 승인·지급 기록과 이번 검토 상태는 별도로 표시한다.
2. **그룹 계산 및 승인 분기.** `representative_name`, `address`, `bank_account_no`로 직접 연결 근거와 그룹을 계산하고, `rebate_amount_krw`를 정산월·그룹별로 합산한다. 요청마다 구성원·금액·연결 근거·승인권자를 보여준다. 관련자 합산은 모든 검토의 기본 동작이다.
3. **사람의 결정.** 승인권자는 승인, 거절, 추가 확인 요청 중 하나를 선택한다. 추가 확인 요청은 확인할 항목·담당자·회신 상태를 남긴다. 임원이 거절하면 사유를 기록하고 정산을 보류한다. 영업지원은 그 사유를 바탕으로 대리점에 소명이나 증빙을 요청한다. 답이 오면 담당자가 검토하고 부족하면 다시 요청한다. 보완이 확인되면 이전 거절 기록을 남긴 채 근거를 첨부한 새 요청을 임원에게 재상신한다.
4. **회계 작업 생성.** 승인되면 회계 지급 검토 작업을 생성하고 승인 근거와 증빙 상태를 연결한다. 필요한 지급 증빙이 미확인이면 회계 작업을 확인 대기로 두고, 확인 회신을 기록하면 지급 검토 가능으로 갱신한다. 지급과 은행 회신은 시연에서 모의 처리한다.

## 서류 처리 확장과 D-024 대조

- AI는 형식이 다른 소명서·계좌 변경 신청서에서 대표자·주소·계좌 후보를 추출한다. 필드별 원문, 페이지나 위치, 추출값을 나란히 표시하며 누락·상충 값은 확인 대상으로 남긴다.
- 주소 표기가 다르면 AI가 동일 주소일 가능성과 비교 근거를 제안한다. 담당자가 원문과 증빙을 보고 수락·수정·반려한다. **담당자가 확인한 값만 등록 정보와 대조**하며, 확인된 동일 주소는 검증된 주소 값으로 비교한다. AI 제안만으로 그룹이나 승인권자가 바뀌지 않는다.
- **원본 확인.** `fin_collection_history_cv.csv`에서 같은 `bank_account_no`를 조회하고 `agency_id`별로 세면 D-011 1건, D-024 2건, D-037 1건이다. 이 계좌는 `m_agency_cv.csv`의 D-011·D-037 정산계좌와 일치하고 D-024의 등록 정산계좌와 다르다. D-024 입금 기록은 `DP-00013`(2026-03-13), `DP-00014`(2026-04-13)이다. 실제 장려금 수취계좌, 계좌 소유자, 변경 여부는 확인 불가다.
- **정책 해석과 추가 통제.** 데이터 사전의 실입금계좌 대조와 W07의 지급계좌 단정 금지는 함께 지킬 수 있다. 원본은 계좌 변경 뒤의 승인 경로 유지 조건을 정하지 않는다. 이 설계에서는 등록정보만 다시 계산한 결과와 실제 승인 경로를 따로 표시한다. 기존 임원 승인 대상 그룹이 변경으로 갈라져도 같은 회수계좌 기록이 남아 있고 관계가 해소됐다는 증빙이 확인되지 않으면, 영향을 받는 건은 **기존 임원 경로를 유지하고 소명 대기**로 둔다. 소명이 확인되면 기존 임원이 증빙과 재계산 결과를 검토한 뒤 보류 해제와 후속 분기를 결정한다. 회수계좌 일치만으로 새로운 관련자 그룹을 확정하거나 지급계좌로 쓰지 않는다.
- 승인권한과 별개로 서류 검토자, 확인 시점, 적용일, 변경 전후 값과 원문 위치를 기록한다. 담당자 확인과 변경 적용은 구분한다. 원본은 보존하고 검증·적용한 변경은 별도 기록으로 관리한다.

## 정정 처리와 시연

| 사례 | 입력과 검증할 결과 |
|---|---|
| 정상 | 원본 2026-06 정산 **40행**을 모두 처리한다. 단독 거래처 37곳은 영업지원팀 **37요청·37행**, D-011·D-024·D-037은 합계 **3,888,097원**으로 영업임원 **1요청·3행**이다. 새 승인 회신에 따라 회계 작업이 만들어지는지 확인한다. |
| 변경 | **모의 신청서**로 D-011 정산계좌가 다른 거래처와 일치하지 않는 값으로 바뀌고 6월 검토에 적용된다고 가정한다. 등록정보 기준으로 D-011·D-024는 대표자·주소 일치로 합계 **2,562,561원**, D-037은 분리되어 **1,325,536원**이다. 금액 규칙만 보면 각각 임원·영업지원 경로다. 그러나 세 곳의 동일 회수계좌 기록이 남아 있으므로 실제 처리는 모두 기존 임원 경로를 유지하고 소명을 요청한다. 앞서 받은 승인은 이력으로 남기고 영향을 받은 회계 작업은 확인 대기로 돌린다. 화면에서 등록정보의 변화와 임원 경로가 유지된 근거를 함께 보여준다. |
| 정보 부족 | D-024의 실제 지급 수취계좌 증빙이 부족한 경우 추가 확인을 요청한다. 금액 승인이 먼저 들어오면 회계 작업을 확인 대기로 생성하고, 담당자가 모의 회신을 확인하면 지급 검토 가능으로 갱신한다. AI 추출·담당자 확인이 회계 후속 처리에 쓰이는 지점을 기록한다. |

정정이 적용되면 해당 적용 범위의 그룹·합계·승인권자를 다시 계산한다. 이전 승인 이력은 보존하고 현재 근거와 달라진 요청을 재검토한다. 그룹·금액·권한이 유지되면 일치 근거와 합산 내역을 보여준다. 시연의 변경 신청서와 외부 회신은 모의 입력이며, 원본 검산과 구분한다. [A01](../01_참가자_배포용/A01.html) · [A04](../01_참가자_배포용/A04.html)

## 상태와 바뀌는 시점

| 대상 | 상태와 전환 |
|---|---|
| 정산 건 | **검토 전 → 검토 중**은 정산월을 열고 그룹·금액을 계산할 때. 상신하면 **승인 대기**. 거절·소명 필요·정정 적용 시 **보류**. 새 요청이 올라가면 **승인 대기**로 돌아가고, 유효한 승인이 기록되면 **회계 검토 중**, 모의 지급·대사가 끝나면 **종료**. 회계 검토 중에도 증빙이 미확인이면 지급 진행을 막는다. |
| 승인 요청 | **초안 → 승인 대기 → 승인 / 거절 / 추가 확인 대기**. 답변을 검토해 보완되면 새 요청을 상신한다. 정정으로 근거가 바뀐 이전 요청은 **재검토 필요** 표시를 붙여 승인·거절 이력과 함께 보존한다. |
| 소명 요청 | **작성 → 답변 대기 → 답변 접수 → 검토 중 → 확인 완료**. 답변이 부족하면 추가 질문을 남기고 **답변 대기**로 돌아간다. 확인 완료는 재상신 또는 회계 증빙 검토에 반영한다. |
| 서류 | **접수 → AI 추출 → 담당자 확인 대기 → 확인 완료 / 반려**. 값이 누락되거나 서로 다르면 확인 대기에서 보완한다. 확인된 변경 신청은 적용일에 별도로 **등록 반영**한다. |
| 회계 작업 | 유효한 승인 후 생성한다. 증빙 미확인이나 관련 변경이 있으면 **확인 대기**, 필요한 증빙과 승인이 갖춰지면 **지급 검토 가능**, 모의 지급 결과를 확인하고 대사하면 **대사 완료**. |

## 원본에 없는 프로젝트 가정

- 서류별 AI 추출·주소 동일 후보 제안·담당자 확인, 변경 적용일과 전후 값의 별도 기록은 이 프로젝트의 확장이다. D-011 계좌 변경 신청과 외부 승인·소명·지급 회신은 모의 입력이다.
- 동일 회수계좌 정황이 남으면 기존 임원 경로를 유지하는 조건과, 임원이 소명을 검토해 보류 해제 여부를 결정하는 절차를 추가했다. 원본에는 실제 지급 수취계좌 증빙, 변경 이력, 구체적인 재승인 절차가 없다.
- 위 상태 이름, 거절 후 대리점 질의·재상신, 증빙이 없을 때 회계 작업을 확인 대기로 두는 절차는 프로젝트 설계다.

## 승인 요청 화면과 소명 발송

| 항목 | 화면과 처리 방식 |
|---|---|
| 승인 근거와 AI 설명 | 화면은 코드가 계산한 그룹 구성, 거래처별 장려금, 월 합계, 승인 기준과 분기 결과를 근거 표로 보여준다. AI는 표와 확인된 증빙을 읽고 **왜 묶였는지**, **묶지 않을 근거 또는 추가 확인할 정보가 있는지**, **승인·거절·추가 확인 요청 중 무엇을 선택할 수 있는지** 요약한다. 반대 근거는 출처와 확인 상태를 표시한다. AI 설명에 들어가는 숫자는 코드가 계산해 전달한 값만 사용하며, AI가 숫자를 계산하거나 만들어 넣지 않는다. |
| AI 호출 실패 | AI 설명은 근거 표와 별도로 불러온다. 호출 오류나 시간 초과 시 **AI 설명 없음 · 근거 표만 확인**을 표시한다. 근거 표, 과거 지급 내역, 권한에 맞는 승인·거절·추가 확인 요청은 계속 사용할 수 있다. |
| 그룹의 과거 지급 내역 | 6월 승인 요청에는 현재 그룹 구성원의 **2026년 1~5월** 원본 내역을 함께 표시한다. `sales_rebate_payment_cv.csv`를 `agency_id`와 `period_ym`으로 조회해 거래처별 `rebate_amount_krw`, `approval_status`, `approver`, `payment_date`를 보여준다. 미지급 행은 미지급으로 표시한다. 현재 구성원 기준 조회임을 표시하고, 과거 그룹 구성이나 실제 은행 처리 여부는 별도 증빙이 없으면 확인 불가로 둔다. 과거 금액은 6월 승인 합계에 포함하지 않는다. |
| 소명 요청서 | AI가 담당자가 선택한 확인 항목, 거절 사유, 계좌 대조 근거를 바탕으로 대리점에 보낼 요청서 초안을 작성한다. 담당자가 수신처·내용·요청 증빙을 확인하고 필요하면 수정한 뒤 발송한다. 발송본과 발송 시점을 남기고, 발송 후 소명 요청을 **답변 대기**로 전환한다. 시연 발송은 모의 처리한다. |
| 건별 독립 처리 | 승인·보류·회계 검토 상태는 정산월 전체가 아니라 승인 요청 단위로 관리한다. 6월 임원 요청 1건이 보류돼도, 그 요청과 별개로 진행할 수 있는 영업지원팀 전결 37건은 각 건의 확인과 승인에 따라 진행한다. 전결 건이 승인되면 해당 회계 지급 검토 작업을 생성한다. |

이 화면과 발송 절차는 프로젝트 구현안이다. 승인권자와 금액 기준은 원본 정책을 적용한다. [W07 안내](../01_참가자_배포용/세계관_BPMN/W07.html) · [승인정책](../01_참가자_배포용/04_원본데이터/00_common/approval_authority_policy.md)

## AI 서류 처리와 재검토 범위

- 텍스트 접수는 정산월과 거래처에 연결한다. 모의 계좌 변경 신청서, 자유 양식 소명서, 기존·새 값 혼합 회신서를 사용한다. 대표자·주소·정산계좌 후보는 원문 줄과 함께 보여주며, 누락·충돌은 담당자가 확인한다. AI 실패 시 직접 입력한다. AI의 입력·응답은 해당 월의 시연 기록에 저장한다.
- 소명 요청서 초안은 대표자·주소·정산계좌·실제 입금계좌 일치 근거와 거절 또는 추가 확인 사유를 참고한다. 담당자가 초안을 수정하고 모의 발송한다. **프로젝트 가정**으로 공용계좌 사용 경위, 거래처 간 관계의 근거, 정산계좌 변경 및 지급 수취 확인 자료 등을 제안할 수 있다. 적절한 증빙의 종류와 충족 여부는 담당자가 판단한다. [W07 안내](../01_참가자_배포용/세계관_BPMN/W07.html)
- 계좌 변경 적용 또는 그룹 확인 시 변경 전후에 연결된 거래처를 포함한다. 6월 지급 검토 건과 같은 해 이전 월인 1~5월의 원본 승인 건을 목록에 올린다. 원본에 지급일이 있는 건은 사후 검토 대상이다. 기존 6월 승인·회계 작업은 재검토 필요·확인 대기로 표시한다. 이 범위와 보류 처리는 프로젝트 가정이다.
- 정산월 목록에서는 거래처별 월 합산과 관련자 그룹별 월 합산의 200만원 초과 건수를 비교한다. 금액은 W07 계산 결과를 사용한다.

### Google Gemini API 전송 항목

- **서류 추출**은 대표자·주소·계좌 후보와 줄 번호를 찾기 위해 선택한 서류의 텍스트 전체를 전송한다. 운영 검증에는 화면에 제공된 모의 서류만 사용한다. 원본 CSV와 등록 마스터는 첨부하지 않는다.
- **소명 초안**에는 거래처 ID, 일치한 필드명, 같은 계좌로 입금한 거래처 ID 목록, 화면에 입력한 결정 사유만 넣는다. 마스터의 이름·주소·계좌 값과 회수계좌번호는 전송하지 않는다. 결정 사유에는 실제 개인·계좌 정보를 입력하지 않는다.
- 서버가 Google Gemini API에 요청하며 API 키는 런타임 환경변수 `GOOGLE_API_KEY`에서 읽는다. 기본 모델은 Gemini 3.1 Flash-Lite이며 `GOOGLE_MODEL`로 지정할 수 있다. 앱에는 요청 본문과 응답 또는 실패 사유를 기록한다. 시간 초과 검증은 기본 모의 서류에만 요청 제한 시간을 1ms로 설정해 실행한다.

- **승인 근거 요약**은 거래처 ID, 일치 항목명, 공동 입금 기록에 연결된 거래처 ID, 승인권자, 한도 초과·재검토 여부, 현재 가능한 선택지를 전송한다. 금액·계좌번호·이름·주소·결정 사유 원문은 보내지 않는다.

- 승인 근거의 사실·승인 선택지는 코드가 표시한다. Gemini는 계산 근거에 연결되는 추가 확인 항목만 선택한다. 이미 결정된 건에는 승인 선택지 문장을 표시하지 않는다.
- 서류 접수의 추가 자료는 제공된 거래처 마스터의 대표자·주소와 원본에 없는 새 계좌번호로 구성한다. 서류를 실제로 추출하면 이 텍스트가 Gemini로 전송된다.
- 원본에서 미지급 건이 있는 정산월만 승인·서류·후속 작업을 처리한다. 제공 데이터의 1~5월은 조회 전용이고 6월은 처리 가능하다. 시연 초기화는 조회 전용 월에서도 수행할 수 있다.
